# Локализация TPI LUX — как это устроено

Сайт собирается на трёх языках из одного комплекта разметки.
Основной язык — **грузинский**, плюс русский и английский.

Никаких зависимостей: нужен только Python 3 (стандартная библиотека).
Ни npm, ни node, ни установки пакетов.

## Быстрый старт

```bash
python3 tools/extract.py     # разметка → шаблоны + словарь
python3 tools/verify.py      # контроль: разметка не поехала
python3 tools/check.py       # контроль качества перевода
python3 tools/build.py       # сборка dist/
```

Готовый сайт — папка `dist/`. Её и заливают на хостинг как есть.

## Что где лежит

```
*.html, styles.css, script.js   исходная разметка (русская) — здесь правят дизайн
src/templates/                  то же самое, но текст заменён на {{ключ}} (генерится)
src/i18n/strings.json           словарь: ключ → {src, ka, en}
src/i18n/glossary.json          согласованные термины
tools/                          четыре скрипта, см. ниже
docs/GLOSSARY.md                выгрузка глоссария для носителя
dist/                           результат сборки — то, что уезжает на хостинг
```

**Разметку правят в корне**, не в `src/templates/` — шаблоны генерируются заново
и ручные правки в них затрутся.

## Рабочий цикл

Поменяли вёрстку или русский текст:

```bash
python3 tools/extract.py && python3 tools/verify.py && python3 tools/build.py
```

`extract.py` не затирает уже сделанные переводы: ключ — это хеш русской строки,
поэтому перестановка блоков ничего не ломает. Изменили русскую строку — она
получает новый ключ, и её перевод корректно показывается как отсутствующий.

Одинаковые строки (меню, футер) переводятся один раз на весь сайт:
из 4100 слов исходника к переводу остаётся **2722**.

## Скрипты

| Скрипт | Что делает |
|---|---|
| `extract.py` | вынимает текст из HTML и `script.js` в словарь, оставляя разметку нетронутой |
| `verify.py` | подставляет русский обратно и сверяет с оригиналом **байт в байт** — страховка от визуальной регрессии |
| `check.py` | проверяет качество перевода, возвращает код 1 при ошибках |
| `build.py` | собирает `dist/` на трёх языках |
| `glossary.py` | выгружает глоссарий носителю (`--audit` — проверяет соблюдение) |
| `mt_batch.py` | режет непереведённые строки на батчи для машинного перевода |
| `mt_codex.sh` | прогоняет батчи через Codex (второй движок) |
| `mt_merge.py` | сводит два движка, проверяет и помечает расхождения |
| `xlsx_export.py` | собирает `.xlsx` для носителя языка |
| `xlsx_import.py` | принимает заполненный `.xlsx` обратно в словарь |

## Почему нужен check.py

Машинный перевод на грузинский даёт дефект, невидимый тому, кто не читает
по-грузински: модель не находит слово и дописывает грузинское окончание к
русскому корню.

Реальный пример из проверки (вывод модели gpt-5.5):

```
საკაბელო трасები
         ^^^^^ кириллица внутри грузинского слова
```

Для носителя это выглядит как явный брак, а на глаз в потоке из 479 строк
не ловится. `check.py` разбирает каждое слово по кодовым диапазонам Unicode
и валит сборку на таком месте.

Кроме этого он проверяет:

- не осталось ли русских слов в `ka`/`en`;
- совпадают ли HTML-сущности (`&nbsp;`, `&mdash;`) с исходником;
- не выросла ли подпись настолько, что перестанет влезать в кнопку или шапку
  (грузинский заметно длиннее русского);
- покрытие перевода и сколько строк ещё числятся черновиком.

## Порядок перевода

1. **Глоссарий вперёд текста.** Носитель вычитывает `docs/GLOSSARY.md` —
   63 термина, из них 27 спорных. Это час работы вместо дня на 479 строк.
2. Согласованные термины возвращаются в `glossary.json` со статусом `done`.
3. Перевод строк идёт уже с зафиксированной терминологией.
   `glossary.py --audit` показывает, где перевод от неё отступил.
4. `check.py` прогоняется на каждом заходе.
5. Финальная вычитка — по собранному сайту, а не по таблице: на этом проходе
   ловят тон и уместность, терминология уже закрыта.

Пока перевод не готов, пустые строки подставляются русским исходником —
сайт остаётся целым на любой стадии, а `check.py` показывает реальный процент.

## Машинный перевод: два движка вместо одного

Носителю отдаётся не пустая таблица, а готовый перевод на проверку — это на
порядок дешевле и быстрее. Чтобы перевод было не стыдно показывать, он делается
**двумя независимыми движками**, а расхождения между ними помечаются.

Почему не Google/Yandex/DeepL:

| Сервис | Почему не подошёл |
|---|---|
| Google Translate (бесплатный endpoint) | IP сервера — датацентровый, отвечает капчей `/sorry/`; официальный API требует платного ключа Google Cloud |
| DeepL | грузинского в списке языков нет |
| LibreTranslate / Argos | грузинского в списке языков нет (проверено по `/languages`) |
| Yandex Translate | грузинский есть, но нужен платный ключ Yandex Cloud |

Готовых скилов или MCP-серверов под грузинский в маркетплейсах тоже нет.
Зато обе LLM переводят грузинский хорошо и, в отличие от NMT-движков, держат
контекст страницы, глоссарий и лимит символов на кнопке — для маркетингового
текста это важнее.

Каждая строка переводится **четырежды**: двумя движками с русского и теми же
двумя движками с английского. Английский переводчик русского текста не видит,
поэтому совпадение результатов — независимое свидетельство, а не эхо одной
и той же ошибки.

```bash
python3 tools/mt_batch.py 40             # 12 батчей с русского
python3 tools/mt_batch.py 40 --from en   # 12 батчей с английского
tools/mt_codex.sh 4                      # Codex: русский → грузинский
tools/mt_codex.sh 4 batch-en             # Codex: английский → грузинский
#   агенты Claude пишут .mt/out-claude-NN.json и .mt/out-claude-en-NN.json
python3 tools/mt_merge.py                # сверка четырёх вариантов
python3 tools/mt_merge.py --write        # результат → strings.json
```

`mt_merge.py` для каждой строки:

- гоняет **все четыре** варианта через проверки `check.py` (смешение письма,
  остатки русского, HTML-сущности) плюс лимит символов для кнопок;
- основным берёт перевод с русского — русский текст первоисточник; если он
  с дефектом, а другой чист, меняет их местами;
- считает похожесть основного варианта с остальными. Посимвольного сравнения
  мало: в грузинском свободный порядок слов и меняются окончания, поэтому
  берётся лучшее из посимвольной похожести и пересечения основ слов;
- строка закрывается, если её подтвердили **два** независимых варианта и
  хотя бы один из них — перевод с английского.

Результат прогона на 468 строках: **382 (83%) закрылись сами**, 86 ушли
носителю. Из них 67 — расхождение русского и английского пути, 32 — расхождение
движков между собой (у части строк обе причины сразу). Дефектов в основном
варианте не осталось ни одного.

Статусы в `strings.json`: `mt-agreed` — переводы сошлись, носителю не
показывали; `mt` — ушло на проверку; `mt-approved` — носитель посмотрел
и принял как есть; `native` — носитель переписал своими словами.

## Обмен файлами с носителем (.xlsx)

Носитель языка не работает с JSON и Markdown, поэтому обмен идёт через Excel.
Единственная зависимость этих двух скриптов — `openpyxl`; venv лежит рядом и
в репозиторий не попадает:

```bash
python3 -m venv .venv-xlsx && .venv-xlsx/bin/pip install openpyxl
```

Выгрузка и приём:

```bash
.venv-xlsx/bin/python tools/xlsx_export.py TPI-LUX-georgian-copy-ГГГГ-ММ-ДД.xlsx
# ... файл ушёл носителю и вернулся заполненным ...
.venv-xlsx/bin/python tools/xlsx_import.py TPI-LUX-georgian-copy-ГГГГ-ММ-ДД.xlsx --dry-run
.venv-xlsx/bin/python tools/xlsx_import.py TPI-LUX-georgian-copy-ГГГГ-ММ-ДД.xlsx
python3 tools/check.py && python3 tools/build.py
```

Три листа: «Инструкция» (памятка носителю на русском и английском), «Перевод»
и «Термины». **В файл попадают только спорные строки** — те, что не закрылись
сверкой четырёх переводов, и только спорные термины глоссария (`status: check`).
Устоявшееся носителю не показывают: его время дорого, а согласие четырёх
независимых переводов надёжнее беглого взгляда на 479 строк. Полная таблица
собирается флагом `--all`.

Что делает файл пригодным для неспециалиста:

- колонка «⚠ Почему строка здесь» объясняет причину сомнения, а рядом лежит
  конкурирующий вариант перевода — тот из четырёх, что дальше всех от нашего;
- строки идут в порядке чтения страницы, а не по алфавиту ключей; сквозные
  элементы меню и подвала собраны в один блок в начале, чтобы не повторяться;
- колонка «Где на странице» переводит служебный контекст на человеческий язык
  («описание страницы для Google», «подпись для незрячих») — это видно из
  вёрстки, но не из словаря;
- надписи, которые CSS печатает капсом (`.section-kicker`, `.badge-new`),
  помечены ⚠ — в грузинском заглавных нет, вёрстку под них правим отдельно;
- бренды, адреса и телефоны помечены «НЕ ПЕРЕВОДИТЬ» и уже заполнены;
- колонка ID и всё, кроме грузинского текста и комментария, защищены от
  случайной правки — пароля нет.

Импорт связывает строки **по ID**, а не по позиции: сдвиг или удаление строк
не портит словарь, испорченные ID выводятся списком и пропускаются. Замечания
переводчика складываются в `docs/native-review-notes.md`.

## Типографика

- **Шрифт.** Inter не содержит мхедрули. Подключён `Noto Sans Georgian`;
  браузер выбирает его по `unicode-range` только для грузинских букв,
  латиница и кириллица остаются на Inter.
- **Заглавные.** В грузинском письме заглавных букв нет, и `text-transform:
  uppercase` для мхедрули — пустая операция. Правило не снято (на грузинских
  страницах остаются латинские надписи, им капс нужен), но для `:lang(ka)`
  добавлена разрядка `0.14em` и увеличен кегль — акцент рубрик возвращается
  другим средством.
- **Интерлиньяж.** У мхедрули выше x-height, поэтому заголовкам на `:lang(ka)`
  задан `line-height: 1.18` вместо тесного латинского.

## Адреса и SEO

```
/                 определяет язык браузера, иначе — грузинский
/ka/…             основной язык, x-default указывает сюда
/ru/…  /en/…
```

На каждой странице проставлены `canonical`, полный набор `hreflang`
(ka, ru, en, x-default), `og:locale` и `og:locale:alternate`.

Переключатель языка сохраняет текущую страницу: со страницы направления
на грузинском вы попадаете на неё же на русском, а не на главную.

Домен задаётся константой `SITE_URL` в `tools/build.py`.
